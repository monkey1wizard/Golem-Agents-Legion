# アーキテクチャ

[English](../../architecture.md) · **日本語** · [繁體中文](../zh-Hant/architecture.zh-Hant.md)

## 技術ベースライン

GAL は Rust で構築されたクロスランタイム開発ワークフローエンジンです。複数の AI プロバイダーにまたがり、統一されたコントロールプレーンと標準化されたワークフロー契約を維持します。本システムの技術基盤は、ソースベースライン、デプロイベースライン、および常設のアーキテクチャ制約から構成されます。

### ソースベースライン

- **Rust ワークスペース**: 7 つのクレート（`gal-foundation`、`mcp`、`dispatch`、`pipeline`、`projection`、`gal-engine`、`cli`）で構成される Cargo ワークスペースであり、統合バイナリ `gal` へコンパイルされます。`dispatch` クレートは、ヘッドレス実行用のバイナリ `gal-dispatch` も生成します。
- **外部データベース非依存**: リレーショナルデータベースやドキュメントデータベースを一切使用しません。すべての状態は、リポジトリ内およびローカルファイルシステム上のプレーンテキストファイルに永続化されます。
- **バージョン管理されるソース契約**: ワークフロー契約、コマンド仕様、エージェントロール定義、およびテンプレートは、`plugins/gal-core/` 配下の Markdown ファイルとして Git で追跡・管理されます。
- **英語正本ベースライン**: リポジトリメタデータの `PROJECT_LANGUAGE` 設定に基づき、契約および主要ドキュメントの権威ある情報源は英語（`en`）と定められています。英語以外の計画成果物は、決定論的ハッシュと等価性スタンプ（equivalence stamp）によって、英語の実行プロンプトとの意味的等価性を維持します。

### デプロイベースライン

- **事前コンパイル済みクロスプラットフォームターゲット**: リリースパイプラインは、`x86_64-pc-windows-msvc`、`aarch64-pc-windows-msvc`、`x86_64-apple-darwin`、`aarch64-apple-darwin`、`x86_64-unknown-linux-musl`、`aarch64-unknown-linux-musl` の 6 つのターゲット環境向けにビルド済みバイナリを生成します。
- **サプライチェーン検証**: リリースアセットには SHA-256 チェックサム（`checksums.txt`）が含まれます。リリースワークフローは `checksums.txt` を Cosign のキーレス署名（keyless cosign）で署名し、`checksums.txt.sig` と `checksums.txt.pem` を公開します。インストールスクリプトは、アーカイブ展開前に SHA-256 チェックサムを必ず検証します。Cosign の署名検証はベストエフォートで行われます。Cosign または署名ファイルが利用できない場合は、警告を出して続行します。検証が完了して失敗した場合は、インストールを中止します。
- **パッケージマネージャーによる配布**: 公式シェルスクリプト（`install.sh`、`install.ps1`）、Homebrew Tap、WinGet、または `cargo install --git` を使用してインストールします。旧式のセルフインストールコマンド（例: `crates/setup`）は廃止されました。
- **Windows 上の静的 CRT リンク**: Windows リリースバイナリは C ランタイム（CRT）を静的リンクしており、Visual C++ 再頒布可能パッケージが導入されていないクリーンな環境でもそのまま動作します。

### 常設のアーキテクチャ制約

- **クロスランタイムでの同等性**: Claude Code、OpenAI Codex、GitHub Copilot、Google Antigravity、opencode においてコントロールプレーンコマンドの挙動を完全に一致させ、ツール間の動作乖離を防止します。
- **リポジトリ所有の状態管理**: `.dev/` ディレクトリ、計画ファイル、調査ドキュメントが、セッション継続性の唯一の情報源（Single Source of Truth）となります。揮発性のランタイムキャッシュがリポジトリ側のファイルに優先することは決してありません。
- **テンプレート駆動のアダプター生成**: リポジトリアダプターファイルは、ソーステンプレートから `gal` バイナリによって自動生成されます。生成されたアダプターファイルを手動で直接編集することは禁止されています。
- **標準的な Git 履歴の維持**: リポジトリ操作には標準の `git merge`、`git commit`、`git branch` を使用します。コミットのスカッシュ（squash）、リベース（rebase）、`--ff-only`、`--no-ff` の使用は禁止されています。並行タスクは履歴を書き換えるのではなく、独立した Git ワークツリー（worktree）上で実行します。
- **スコープの完全性**: プロジェクト所有者が開発目標とスコープ境界を定めた後、エージェントが一方的にスコープを縮小したり、未承認のフェーズへ機能を分割したり、勝手な KEEP リスト（残存リスト）を導入したりすることは禁止されています。
- **厳格なトークンおよびファイル予算**: プロジェクトインデックス `.dev/project.md` の推奨上限は 30,720 バイト、`.dev/state.md` の推奨上限は 16,384 バイトです。上限を超えると、`gal finalize-check` は `project-md-bound` 行と `state-bound` 行で `advisory` を報告し、GAL は `plugins/gal-core/conventions/token-budget.md` に従って修復します。また、アダプターファイル内のワークフロー遵守マーカー（workflow obedience marker）は、Codex の既定の `project_doc_max_bytes` の境界であるバイトオフセット 32,768 より前に配置し、部分読み取りが行われた場合でも重要な制約が確実に読み込まれるようにします。

## ディレクトリ境界と依存関係の法則

コードベースは厳格なモジュール分離と、下位方向のみを指す一方向の依存階層を徹底し、循環参照を防止します。

### クレート依存グラフ

クレート間の依存関係は、厳密に下位方向のみを指す有向非巡回グラフ（DAG）を形成します。

```text
gal-foundation  （基盤レイヤー: 内部 gal クレートへの依存ゼロ）
dispatch        （gal-foundation のみに直接依存）

dispatch   ─> gal-foundation
mcp        ─> gal-foundation
projection ─> gal-foundation
pipeline   ─> dispatch
gal-engine ─> gal-foundation, projection
cli        ─> gal-foundation, mcp, projection, dispatch, pipeline, gal-engine（バイナリエントリーポイント）
```

### クレート責務マトリクス（禁止境界）

| クレート | 責務 | 禁止される操作 |
| --- | --- | --- |
| `gal-foundation` | 設定構造、パスユーティリティ、OS 抽象化、ランタイムレジストリ（`VALID_RUNTIMES`）、MCP スキーマ、`HealthCheck` トレイト、`secret_re` などの共有基盤。 | 他の GAL クレートへの依存、および CLI コマンドの実装。 |
| `mcp` | MCP 成果物の管理: 正規 `.mcp.json` のヘルスチェックなど。 | `claude_desktop_config.json` など、ホスト管理の設定ファイルの検査、編集、書き込み。 |
| `dispatch` | ヘッドレス実行: ロールルーティング（`executorRouting`）、プロセスタイムアウト、write-back 検証、SSH 実行レーン。 | `pipeline` が担当する複数フェーズのワークフローオーケストレーション、および `gal-foundation` 以外のクレートへの依存。 |
| `pipeline` | ワークフローオーケストレーション: タスク分解、複数フェーズのディスパッチ、タスク仕様の組み立て。 | OS のプロセス生成 API の直接呼び出し、およびランタイムファイルのプロジェクション。 |
| `projection` | ファイルプロジェクションエンジン: スキル、コマンド、指示文、エージェントを各ランタイム操作面へ配布。 | リポジトリレベルのアダプター（`AGENTS.md`）の生成、およびヘッドレスエグゼキュータープロセスの管理。 |
| `gal-engine` | ワークフロー CLI プリミティブ: 正規ルートのレンダリング（`~/.gal/plugins/gal/`）、CLI 型定義、doctor チェック、Git フィルターフック。 | 外部ツールのパスへの直接プロジェクション、および `dispatch` や `pipeline` の直接呼び出し。 |
| `cli` | 実行可能エントリーポイント: 引数解析、`gal doctor` の集約、アダプター生成（`render.rs`）、内部検証ゲート。 | 事前検証（preflight）の回避、および境界を越えたクレート内部構造への直接アクセス。 |

Golem-Agents-Legion/
├── plugins/
│   └── gal-core/                正規のソース契約群

│       ├── templates/           リポジトリ状態テンプレート [Protected]
│       ├── agents/              Golem エージェント契約（*.agent.md）
│       ├── skills/              再利用可能スキル（skills/<name>/SKILL.md）
│       ├── codex/               Codex フック設定（hooks.json）
│       ├── hooks/               Git フック（commit-msg、pre-commit）

### ワークツリー内のランタイムレーン

`source-worktree` は正規ワークツリー内の不変な実行ファイルで検証します。`downstream-installed` リポジトリはパッケージマネージャーがインストールした実行ファイルを使用します。共有実行ファイルをインストールまたは昇格できるのはパッケージマネージャーだけです。`CoordinatorState.execution_binding` が唯一の永続的なバインディング権威です。信頼するレシートにはそのダイジェストを記録します。

```text
(start) gal コマンドが信頼できる実行ファイルを必要とする
  │
  ▼
{ どの実行レーンか? }
  ├── source-worktree ──────▶ [ target/gal-pipeline/ 内のプライベート世代 ] ─┐
  └── downstream-installed ─▶ [ パッケージマネージャー導入の実行ファイル ] ──┤
                                                                             │
  ┌──────────────────────────────────────────────────────────────────────────┘
  ▼
[ バインディング、実行ファイルのパス、ハッシュ、レシートのダイジェストを検証 ]
  │  @CoordinatorState.execution_binding
  ▼
{ バインディングは有効か? }
  ├── 欠落または不一致 ──▶ (end ×) 強制停止
  │
  有効
  ▼
[ 信頼する操作を実行 ]
  │
  ▼
{ 安全な区切りで再ビルドが必要か? }
  ├── いいえ ──▶ (end √) バインド済み実行ファイルで続行
  └── はい ────▶ [ 新しい不変世代へ再バインドし、以前のバイト列を保持 ]
                   │
                   ▼
                 (end √) 新しい世代で続行
```

### パイプライン試行の所有権と証拠

#### ホストサブエージェント (host subagent) 試行とコーディネーターのバインディング

ホストサブエージェントの実行はホストが管理し、パイプラインの権限に参加しますが、サブエージェントがオーケストレーターと同じオペレーティングシステムのプロセスを共有するとは主張しません。各試行は、選んだホスト、タスクとフェーズ、試行の同一性、モデルと tier、完了状態、返された証拠を結び付けます。試行のオープンとクローズ、範囲内の結果の検証は、オーケストレーターが担います。

guarded 継続では、ホストサブエージェントの再開は、コーディネーターによる checkpoint の永続的な公開に結び付けられます。ドライバーは、`resume_host_subagent` JSON アクションが使う正確なバインディングを出力します。legacy クローズは `--close` と `--session` を使います。どちらの経路でも、既存の run pin は変更できません。

パイプラインは、正規プロンプト（canonical prompt）への書き込み操作を prompt-writer リース（prompt-writer lease）によって直列化します。プロンプトの不変スナップショットを取得し、変更可能なフェーズ状態を準備する前に、まずこのリースを取得します。続いて receipt リースを取得し、レシートの配置、終了エビデンスの収集、およびプロセスのクリーンアップ完了を確認した後にのみ、両方のリースを逆順で解放します。プロセスのクリーンアップを確認できない場合、GAL はすべてのアクティブなリースと復旧用成果物を保持します。パイプラインの試行（attempt）は、receipt リースの保持中に検証済みレシートのバイト列とそのダイジェストを取得・保存します。フェーズの書き戻し処理はこの不変スナップショットを直接参照し、解放済みのディスク上レシートパスを再読み込みしません。最終ゲート検査では、ディスク上のレシートがこのスナップショットと一致することを検証します。GAL がロックの経過時間のみに基づいてリースの所有権を推定することはなく、放棄されたリースを自動的に引き継ぐこともありません。

ワークフローの継続（`from <task>`）と、実行可能なフェーズやタスクの引数は、互いに独立したインターフェースです。不正または無効な継続入力はプロセス起動（spawn）前の検証でエラーとなり、既定タスクの実行へフォールバックすることはありません。ディスパッチされた Codex の子プロセスは、親セッションの承認モードにかかわらず `--dangerously-bypass-approvals-and-sandbox` 付きで起動され、Codex のサンドボックス外で動作します。これは、Codex の Windows サンドボックスが現在コマンドを実行する前に失敗するためです。実行ファイルの探索（availability lookup）、プロセスの起動、プロバイダーの応答、プロセスの終了状態、レシートの検証、およびゲート判定結果は、それぞれ独立した証拠段階として追跡されます。ユーザー向けの Codex 設定および復旧ワークフローについては、[セットアップ](setup.ja.md#codex-パイプライン実行のセットアップ) を参照してください。ツールが yield した後に元のセッションの完了を待つためのホスト側の契約は、`gal-pipeline` スキルの `Headless Executor Dispatch` で定義されています。

#### ガード付きコーディネーターの所有権

`legacy_interactive` はデフォルトの継続プロファイルです。既存の Claude Code と OpenCode のホスト所有の監視および継続ループ、呼び出し構文、プロセス終了動作、プロジェクションのレイアウト、`EvidenceContract: v1` のレシート、マーカー、変更順序のセマンティクスを維持します。通常の `gal pipeline <prompt>` コマンドはガード付きモードを選択しません。

`codex_stop_v1` は、信頼された Codex フックのハンドシェイクが有効なワンタイム・グラントを提示した後にのみ選択されます。このプロファイルでは、各 `gal pipeline` 呼び出しが 1 つのブロッキングな機械処理セグメントを実行します。Rust コーディネーターは、タスクとフェーズの遷移、試行のライフサイクル、再試行状態、型付きアクション、証拠チェック、ジャーナル復旧、上限付きステータスを管理します。セグメントは、型付き ORCHESTRATOR チェックポイント、終端結果、人間の権限が必要なブロッカー、または回復不能な証拠エラーに到達すると戻ります。

コーディネーターは意味的な判断を行いません。同じ ORCHESTRATOR スレッドが、タスク品質レビュー、境界拡大の判断、収束の判断、ゴールから逆算した検証を担当します。コーディネーターは、型付きの次アクション `await_orchestrator` を持つチェックポイントを永続化します。ORCHESTRATOR は、そのチェックポイント、コーディネーターのリビジョン、プロンプトまたは仕様のハッシュ、コミットにバインドされたレシートを提出し、その後に型付き再開アクションを呼び出します。後続のブロッキング CLI セグメントは永続化された状態を再び開きます。GAL はデーモン、再帰的なシェル呼び出し、隠れたスーパーバイザー、モデル判断を待つプロセス内待機を使用しません。

ガード付きエントリーの後、コーディネーター状態は既存の `.dev/pipeline/<plan-scope>/` 権限領域に置かれます。アトミックな単一ファイル書き込みによって、プロンプトとリポジトリ、現在のタスクとフェーズ、アクティブな試行、再試行状態、最後に検証された証拠、保留中のプロジェクション・トランザクション、ORCHESTRATOR チェックポイント、アクティベーション・ダイジェスト、次のアクションをバインドします。コーディネーターが担当するのは機械的処理だけです。意味的な権限は ORCHESTRATOR が保持し、Stop フックが時期尚早な最終応答をブロックした場合も、ホストブリッジが同じスレッドを継続します。

#### プロセス ID とディスパッチ証拠

すべての v2 ディスパッチは、プロセス起動前にその意図を永続化します。試行の ID は、ホスト、PID、オペレーティングシステムのプロセス生成 ID、試行 ID、プロンプトとリポジトリ、ベースコミット、想定フェーズをバインドします。GAL は該当する試行を待機またはアタッチします。PID だけから所有権を推定することはありません。所有権が不明であるか、記録された ID と競合する場合、GAL はリースを回収せず、プロセスを終了せず、作業を再ディスパッチしません。

`EvidenceContract: v2` は、プラン、タスク、フェーズ、試行、レシート・ダイジェスト、プロバイダー・セッション、プロンプトまたは仕様のダイジェスト、テスト対象のコミットまたは差分へのバインディングを追加します。下流のゲートが試行を分類する前に、成功したプロバイダー・セッションの ID とプロヴェナンスがディスパッチ結果、終端試行ログ、v2 証拠で一致していなければなりません。v2 の Agy パスは、試行に属する同じプロセスまたは SSH 標準出力が生成した上限付き JSON 出力から、ネイティブのセッション UUID を読み取ります。出力がない場合、形式が不正な場合、重複している場合、一致しない場合、切り詰められている場合、またはサイズ超過の場合は、型付き証拠エラーになります。再開したディスパッチは、要求されたセッション UUID を返さなければなりません。

バイナリーゲートは、同じ試行とテスト対象の変更にバインドされた証拠から v2 の Three-Condition PASS ルールを評価します。より新しいコードの検証に、過去の `completed` 証拠を使用することはできません。v2 証拠がないか曖昧な場合、意味的な TEST または AUDIT の再試行回数を消費せず、自動再ディスパッチも行いません。これらの追加事項は、v1 のレシート、終了コード、公開 `Dispatch:` マーカー、CLI、変更順序の契約を変更しません。

#### 永続状態とクラッシュ復旧

ガード付きセグメントがプロバイダーを起動する前、またはタスクカーソルや進捗プロジェクションを変更する前に、保留中のプロジェクション・ジャーナルを復旧し、復旧したバインディングに対して新しいパイプライン・プレフライトを実行します。再開では、セグメント固有の新しいプレフライト・レシートを使用します。レシートがない、古い、失敗している、形式不正である、または書き込み不能である場合、プロバイダーの起動や権限の変更より前にセグメントを停止します。稼働中の所有者には読み取り専用でアタッチします。孤立したコーディネーターは、アクティベーション・ダイジェストと試行 ID が一致する場合に限り、検証済みの永続状態から再開します。所有権が不明であるか競合している場合は、型付き競合で停止します。

プロンプト、ソースプラン、`.dev/state.md` にまたがるタスクの進捗は、永続化されたプロジェクション・ジャーナルを使用します。ジャーナルには、意図したトランザクション、ステージング済みの対象バイト列、変更前と変更後のハッシュを記録します。復旧は、対象が記録された変更前または変更後のハッシュと一致する場合にのみ置換を適用します。これらのハッシュによって所有権が確立される場合は、中断されたトランザクションを冪等に完了します。対象に第三者のハッシュがある場合、復旧を停止してその内容を保持します。コーディネーターは、ジャーナルがプロジェクションのコミット済みを示した後にのみ、永続状態を進めます。

```text
(start) ガード付きセグメントがコーディネーターを開く
  │
  ▼
{ コーディネーター状態があるか? }
  ├── なし ──▶ [ 起動前に状態とディスパッチ意図を永続化 ]
  │              │
  │              ▼
  │            (end √) ディスパッチを開始
  │
  あり
  ▼
{ 所有者の ID は? }
  ├── 正確な稼働所有者 ──────▶ (end >>|) アタッチして待機、再ディスパッチしない
  ├── 不明または競合する ID ──▶ (end ×) 型付き競合で停止
  │
  一致する孤立状態
  ▼
[ 射影ジャーナルを復旧 ]
  │
  ▼
{ ジャーナルの対象ハッシュは? }
  ├── 第三者のハッシュ ──▶ (end ×) 対象を保持し、競合で停止
  ├── 変更前ハッシュ ────▶ [ ステージング済み置換を適用 ] ─┐
  └── 変更後ハッシュ ────▶ [ 置換を完了として記録 ] ───────┤
                                                           │
  ┌────────────────────────────────────────────────────────┘
  ▼
[ ジャーナルをコミットしてから、新しいプレフライトを実行 ]
  │
  ▼
{ プレフライトのレシートは合格か? }
  ├── いいえ ──▶ (end ×) プロバイダー起動前に停止
  └── はい ────▶ (end √) コーディネーター状態を進める
```

`legacy_interactive` は、既存のホスト所有の復旧および継続動作を維持します。Codex のマーカー、canary、フック、グラント、またはコーディネーター所有の継続は必要ありません。

## データ変換パイプライン

ビルドパイプラインは、Git で追跡されるソース契約群を、各ランタイムのプロジェクション操作面およびリポジトリローカルのアダプターファイルへ変換します。

### アーキテクチャ統制

本ドキュメントはモジュールの所有権とデータフローを規定します。ソース契約は、リポジトリアダプター生成器と正規ルートレンダラーへ別々に渡されます。その後、プロジェクションエンジンがコンパイル済みのアセットを各ランタイムへ配布します。ファイルレイアウト、パス解決、トランスポート、プロジェクションレジストリに関する技術的な詳細は [プロジェクション](projection.ja.md) で定義されています。また、ユーザーが設定可能な設定境界は [設定](configuration.ja.md) で定義されています。

## 使用量記録

GAL は、ディスパッチされた実行ごとに各ランタイムが報告する使用量を記録します。また、その使用量の背後にある共有アカウントの容量も報告します。唯一の契約は [`usage-accounting.md`](../../../plugins/gal-core/conventions/usage-accounting.md) です。本節はアーキテクチャを要約します。両者が食い違う場合は、契約が優先されます。

### 証跡ストアと取得

- 証跡は Git の共通ディレクトリ配下の `gal/usage/v1/` に保存されます。パイプラインのクリーンアップとリンクされたワークツリーの削除後も、ストアは残ります。ファイナライズは会計の証跡を保持し、変更しません。
- 取得は、単独、ローカル、SSH、ホストサブエージェントの各試行が終了するすべての経路の後に実行されます。再試行または再開は、セッションの系譜を保ったまま新しい試行を作成します。
- 取得に失敗しても、実行結果、再試行ポリシー、レシートは変わりません。レポートは、部分的または利用不可の会計を理由とともに表示します。
- プリフライトは、一意に特定できる識別情報を見つけた場合にのみ、オーケストレーターのセッションを紐付けます。見つからない場合、レポートはその識別情報を利用不可と表示します。GAL が会話を自動的に選択することはありません。

### 事実記録と評価

- コレクターは観測値とスナップショットを追記します。スナップショットには、観測の正確な集合、調整バージョン、レートセットのダイジェストを記録します。
- 発行によって既存の記録が置き換わることはありません。内容が同一であれば、変更なしに再生されます。同じ識別子でバイト列が異なる場合は、競合として失敗します。
- 評価は分類結果のみを追記します。1 つの評価は 1 つのスナップショットと、分類対象の安定した貢献 ID を指定します。
- 評価の入力に事実のフィールドが含まれていると、終了コード 64 で失敗します。事実のフィールドには、価格、トークン数、合計、クォータのフィールド、未知のフィールドが含まれます。
- いかなる評価、レポート、レビューも、事実のスナップショット、レシート、目標検証の結果を書き換えません。目標検証はオーケストレーターのプロセス内に残り、使用量コマンドはそれをディスパッチしません。

使用量コマンドは次のとおりです。

```text
gal usage collect --run <run-id> [--binding <path>] [--rates <path>]
gal usage report --run <run-id> [--snapshot <snapshot-id>] [--assessment <assessment-id>] [--json]
gal usage assess --run <run-id> --snapshot <snapshot-id> --input <path>
```

### 重複する指標と再試行

親セッションは、子セッションを含む合計を報告することがあります。GAL は各子セッションを 1 回だけ数えます。照合用のフィクスチャでは、親が 200 出力単位を報告し、その中に 60 単位の子セッションが含まれています。タスクの合計は 200 であり、260 ではありません。

100 単位を消費した失敗した試行と、60 単位を消費した成功した再開の合計は、タスクで 160 になります。各試行の結果は、それぞれ別個の判断として扱います。

### コスト、クレジット、請求

各見積もりは、プロバイダーが報告した金額、レートから導いた推定値、確認済みの請求額という 3 つの値を別々に保持します。GAL はこれらの値を合算しません。

- レートに基づく推定には、オーナーが提供したレートセットが必要です。GAL はレートを取得しません。レートが欠けているか曖昧な場合、推定は不明となり、ゼロとは扱いません。
- クレジット、サブスクリプションの枠、通貨は別々の単位です。GAL はそれらを互いに換算することも、請求額に換算することもありません。
- 確認済みの請求額には、同じ範囲の課金根拠が必要です。クォータの変化は請求ではありません。

例えば、レートセットに観測されたモデルのレートがない場合、レポートは `estimate: unknown` と表示します。単位の合計は変わりません。

### アカウントクォータの能力マトリクス

クォータは共有アカウントの容量を表します。タスクの使用量ではなく、どのフローもクォータからタスクのコストを導きません。

| ランタイム | 受動的な情報源 | 制御読み取り | ギャップの扱い |
| --- | --- | --- | --- |
| Codex CLI | なし。標準出力にクォータは含まれません。 | 上限付きの `codex app-server` RPC 読み取り。 | 読み取りに失敗した場合、理由とともにギャップを記録します。 |
| Claude Code | ストリーム出力の `rate_limit_event`（存在する場合）。 | なし。 | イベントに含まれないウィンドウは、ゼロではなく不明です。 |
| GitHub Copilot CLI | なし。usage ブロックにクォータのスナップショットはありません。 | なし。 | ギャップは検証済みの CLI 1.0.98 に固定されます。 |
| Antigravity CLI | 出力に含まれる構造化 JSON のクォータ（存在する場合）。 | なし。 | ヘッドレスのトークン使用量は、アカウントのクォータではありません。 |
| OpenCode | なし。 | なし。 | ギャップとともに、プロバイダーの識別情報を表示します。 |

2026-10-17 の能力監査では、インストール済み CLI のバージョンを記録しました。有料のプロバイダーリクエストは実行していません。また、すべてのランタイムでライブのクォータ受け入れ試験は実行していません。この監査の時点では、OpenCode は PATH 上にありませんでした。契約は 2026-10-20 に公開されました。

ネイティブのウィンドウは、種類、期間、単位、方向を保持します。GAL はそれらを 5 時間と週次の組に無理に当てはめません。欠けているウィンドウを、ゼロや無制限として扱うこともありません。

### フィクスチャによる検証と実ソースの受け入れ

フィクスチャのテストは、記録された入力を使って、パーサー、照合、レポートを検証します。実ソースの受け入れは、明示的に選んだセッションを使い、上限付きのライブハーネスで行います。プロバイダーの CLI をインストールすることも、ログインを開始することもありません。フィクスチャの結果は、実ソースでの動作を証明しません。

制御読み取りは、推論を伴わないプロトコルの読み取りです。そのトレースはプロトコルの動作を示しますが、プロバイダーの課金保証を証明するものではありません。GAL はプローブの方法と所要時間をメタデータとして記録します。また、プローブに費用がかからなかったと述べることは決してありません。

### 信頼されたローカル運用者の制限

使用量の証跡は、信頼されたローカル運用者を前提としています。ストアは通常のローカルファイルストアです。整合性と競合の検査は、不整合な記録を検出します。ただし、Git の共通ディレクトリへの書き込み権限を持つ者が記録を編集していないことは証明できません。

## コンポーネントモデル

内部コンポーネントは単一責任の原則に従って分離され、曖昧さのない統一された用語を使用します。

### 用語規則

使用する用語は、[`docs/glossary.md`](../../glossary.md) の権威ある用語集に厳格に従います。

- ファイル配布エンジンには、曖昧な「adapters」という呼称ではなく `projection` を使用します。
- 外部ランタイム向けのロジックは、厳格に `projection` クレート内にカプセル化します。
- ヘッドレス CLI ランナーには、過去の `dispatch::adapters` に代えて `executors` を使用します。
- 非推奨となったコンポーネントは、未使用のスタブを残すことなく完全に削除します（例: `crates/xmachine` の完全削除）。
- 一時的なタスク識別子（`T-NN`、`R-NN`）や移行経緯の叙述を、恒久的なドキュメント内に残してはいけません。

### アダプター生成とプロジェクションの分離

リポジトリアダプター生成、正規プラグインレンダリング、ランタイム操作面へのプロジェクションは、互いに独立した 3 つのモジュールで実行されます。

1. **リポジトリアダプター生成**（`crates/cli/src/gal/render.rs`）: `.dev/project.md` の必須 8 セクションを抽出し、`AGENTS.md` を生成します。`projection` を使用しません。埋め込みソースの解決のみに `gal-engine` を呼び出します。
2. **正規プラグインレンダリング**（`crates/gal-engine/src/render/`）: `plugins/gal-core/` と `~/.gal/local/` を統合し、`~/.gal/plugins/gal/` を構築します。
3. **ランタイム操作面へのプロジェクション**（`crates/projection/`）: 正規ルートから `~/.agents/skills/` や `~/.codex/agents/` などのツールディレクトリへ成果物を投影します。

### Golem エージェントロールの分類

エージェントペルソナは、その呼び出し能力に基づいて以下の 2 つのクラスに大別されます。

- **クラス 1: 直接呼び出しおよび対話相談が可能なロール**
  - `golem-architect`、`golem-analyst`、`golem-designer`、`golem-releaser`、`golem-debugger`、`golem-steward` の 6 ロール。
  - `/gal <role>` で直接呼び出すことができ、隔離されたサンドボックス内で評価を実行して構造化された要約を返します。
  - そのうち 4 ロール（`architect`、`analyst`、`designer`、`releaser`）には、同名のスタンドアロンコマンドもあります。その `discuss` 引数は、内部の `gal consult-script golem-<role>` を通じてコンテキスト内相談を開始します。Claude Code では `/<role> discuss`、プラグインモードでは `/gal:<role> discuss`、Codex では `$<role> discuss` を使用します。削除された `/gal discuss <role>` 形式は `COMMAND: error` と代替コマンドを返します。debugger にはスタンドアロンコマンドがなく、steward のスタンドアロンコマンドは `discuss` に対応しません。
  - 4 つのレビュー系ロールの隔離モード直接呼び出しは、`ROUTING_SCOPE: codex-native-projection-only` を出力します。`planning` 設定は Codex ネイティブエージェントのプロジェクションにのみ反映され、エグゼキューターは起動せず、SSH フィールドも適用されません。
- **クラス 2: オーケストレーター駆動のロール**
  - `golem-implementer`、`golem-tester`、`golem-auditor`、`golem-researcher` の 4 ロール。
  - **プロジェクション制約**: プロジェクションエンジン（`crates/projection/src/lib.rs` の `update_skills`、`ORCHESTRATED_ONLY_GOLEM_NAMES` を使用）が、これら 4 ロールのプロジェクションファイル（`*.agent.md` または `*.toml`）を作成することは厳格に禁止されています。
  - **安全な fail-closed 設計**: `/gal tester` や `$tester` などを直接実行すると、`COMMAND: error` が返ります。その `ACTION:` 行は、ロールがオーケストレーター専用であることを示し、`/gal pipeline` または `/gal research` の利用を案内します。これらのロールは、`/gal pipeline` などのオーケストレーターから起動されるヘッドレスなサブプロセスとしてのみ実行されます。

## システム境界と統合

GAL は、明確に定義された境界を介して各ツールランタイムと連携します。本ドキュメントでは契約、正規レンダラー、プロジェクション、リポジトリアダプター間の構造的分離を定義しています。具体的なトランスポート機構とファイルパスは [プロジェクション](projection.ja.md) を、設定スキーマは [設定](configuration.ja.md) を、オプションの外部統合は [統合](integrations.ja.md) をそれぞれ参照してください。

## 進化と移行のポリシー

アーキテクチャ上のガードレールにより、後方互換性の維持と安全なアップグレードを実現します。

### 互換性維持のパターン

- **Serde フィールドエイリアス**: 設定キーや内部属性の名前を変更する際は、`#[serde(alias = "...")]` 属性を付与して、既存の `config.json` や `plugins.lock.json` との互換性を維持します。
- **安全なディレクトリクリーンアップ**: 古いディレクトリは、明示的な GAL 所有権マーカーが存在し、かつ空である場合にのみ削除されます。ユーザーファイルが含まれている場合は処理を中断しない警告を出力し、ディレクトリを安全に保持します。
- **Golden テストの同期更新**: テンプレートの出力形式や契約フォーマットを意図的に変更した場合は、対応するテストスイートおよびゴールデンテストのフィクスチャを、変更理由のドキュメントとともに同一コミット内で更新しなければなりません。

### エスカレーション基準

以下の作業が必要となった場合は、直ちに実装を中断し、`/deep-planning` を通じてアーキテクトレビューを要求してください。

- ルート設定ファイル（例: `Cargo.toml`、`package.json`）の新規作成または削除。
- 外部依存クレートの追加または削除。
- アーキテクチャレイヤー境界をまたぐファイルの移動。
- 新たなグローバルインターフェースや抽象基本型の導入。
- 複数の利用者が参照する公開 API シグネチャまたは共有モジュールインターフェースの変更。
- 3 つ以上のコンポーネントで共有される中核的な抽象概念の変更。
- 保護対象パス（Protected Paths）内のファイルの編集。

### 恒久的ナレッジコア

以下の成果物はリポジトリの恒久的なナレッジベースを構成するものであり、セッションをまたいで確実に維持されなければなりません。

- **ソース契約**: `plugins/gal-core/` 配下のコマンド、規約、ワークフロー、およびテンプレート。
- **用語の権威**: [`docs/glossary.md`](../../glossary.md) の正規用語集、ならびに [`docs/i18n/zh-Hant/terminology.zh-Hant.md`](../zh-Hant/terminology.zh-Hant.md) および [`terminology.ja.md`](terminology.ja.md) のロケールプロファイル。
- **公式ドキュメントおよび ADR**: `docs/` 配下のトピックガイド、および `docs/adr/` 配下のアーキテクチャ決定記録。
- **プロジェクト仕様**: 高密度なプロジェクトメタデータを保持する `.dev/project.md` マニフェスト。

## ドキュメント統制

### 恒久ナレッジの境界

恒久的なナレッジベースが配置される場所は、ルートの 3 ドキュメント（`README.md`、`SECURITY.md`、`CONTRIBUTING.md`）および正規の `docs/` ディレクトリの 2 箇所に厳格に限定されます。

`.dev/plans/`（一時的な機能計画）や `.dev/research/`（探索的な調査メモ）などのディレクトリは、恒久ナレッジベースの外部に位置付けられます。開発中に判明した知見は、`docs/` へ統合されるか、または計画内で正式化された場合にのみ恒久化されます。`.dev/project.md` ファイルは、孤立した事実を無秩序に蓄積するのではなく、`docs/` を参照する圧縮された索引として機能します。

### 構造マップ

`docs/structure/structure-map.ndjson` は二軸の構造マップです。コード軸はファイルとディレクトリを、ドキュメント軸はドキュメントのセクションを追跡します。各行は 1 つのノードで、`syncStatus`、`lastSynced`、`lastSyncedRef` フィールドを持ちます。行の形式は `docs/structure/structure-map.schema.json` で定義されます。コードの変更が文書化された動作に影響する場合、`doc-sync` ワークフローがこのマップを更新します。

### 句読点ポリシー: セミコロンの禁止

本リポジトリのすべてのドキュメントでは、言語を問わず半角および全角のセミコロン（`;` / `；`）の使用を禁止しています。セミコロンは複数の思考を単一の文に詰め込む傾向を生みます。執筆者は、独立した思考を別々の文に分割するか、適切な接続詞を用いて文構造を明確にしてください。セミコロンで区切られた一覧は、読点区切りまたは箇条書きとして表現します。

このポリシーは可読性と論理構造の明確さを最優先するためのものであり、本文、表のセル、図、コードコメントに適用されます。なお、プログラミング言語の構文上不可欠なセミコロンは例外として認められます。

### 文章品質の責務

現在のエージェントは、実際の送信前の草稿にある重要な事実の主張を、利用可能な具体的根拠と一つずつ照合します。裏付けのない主張は削除するか、適切な限定を加えます。完了を示す証拠がないことは、作業が未着手である証拠にはなりません。成果物だけを求められた場合は従います。ただし、優先度の高いホスト指示が別の出力を要求する場合は除きます。

GAL は、移植可能な文章要件、プロジェクト用語、および本リポジトリの任意の文章チェック統合を管理します。`docs/glossary.md` は意味上の名称と英語の語彙を定義します。zh-Hant と ja の用語プロファイルは各言語の表記と句読点を定義します。文章規約は言語をまたぐ文章構造とルールの責務を定めます。実行可能な用語データは、これらの文書にある明示的な構造化ブロックからのみ生成します。周辺の文章からルールを推測しません。

リポジトリのチェッカーは、文書ルートの `.dev/cache/writing-terms/<sourceHash>.json` に不変の用語スナップショットを公開します。既存のスナップショットを検証して再利用し、他の書き込み元のデータを置き換えません。子プロセスは、実際に読み取った権威文書と親プロセスのソースハッシュを照合します。直接の CLI 呼び出しと公式 MCP は自身の文書ルートを解決し、一致する既存のスナップショットを要求します。欠落、破損、古いデータは運用上の失敗になります。これらの直接経路では、事前の明示的な生成が必要です。

書き手は実際の受信者の知識に合わせ、必要な背景を示します。事実の出典は依頼、提供資料、または実際に観測したツール結果です。書き手は事実を推論、仮定、提案、仮置きの内容、将来の約束と区別します。進捗を含む人向けの全メッセージで、正確さと読みやすさを作成中に自己レビューします。設定済みのチェッカーが利用可能なら、送信前の草稿を検査します。この義務だけでは、ホストによるストリーム出力の遮断を証明できません。

GAL Core は中立的な最低要件と完全な文章規約への参照を提供します。個人用の `accurate-answer` 指針を複製せず、依存もしません。個人用指針よりプロジェクト用語と必須の出力構造を優先します。個人用指針が存在しない場合や無効な場合も、最低要件は適用されます。

呼び出し元は明示的な意図、対応する `lang` メタデータ、既知の管理対象パスの順にロケールを解決します。`zh-Hant` を `zh-TW` に対応付けるのは、管理対象の `docs/i18n/zh-Hant/` 文書だけです。すべての繁体字中国語文書を台湾中国語と分類するものではありません。コマンド、コード、パス、リンク先、フロントマター、機械用アンカー、ID、レシート、逐語引用は引き続き保護します。

wrapper は `--transport cli` と `--transport mcp` に対応し、両経路で同じ形式の GAL 指摘と実行レポートを生成します。MCP 経路は公式サーバーを使います。ハンドシェイクが成功した場合は、サーバーが通知した名前とバージョンも記録します。ネイティブ textlint CLI/MCP の出力は低レベルの診断形式であり、完全な GAL レポートではありません。

ソースの規約ファイルがある場合、簡潔なルート指針とタスク指針はそのファイルを参照します。別の初期化済みリポジトリでは、`~` をユーザーのホームに展開し、`~/.gal/plugins/gal/rules/gal.md` の writing-quality.md 節を参照します。既存のインストール済み標準ルールファイルを使うため、私有ソースチェックアウトや個人用の文章スキルは不要です。Claude は簡潔な `@AGENTS.md` インポートを維持します。

### ファイル命名規約

- `README.md` はリポジトリルート専用のファイル名です。サブディレクトリで目次ドキュメントが必要な場合は、厳選された概要には `guide.md` を、構造化された一覧には `index.md` を使用します。
- `docs/integrations.md` 内のツールセクションには正式な製品名を使用します。MCP サーバー専用のセクションにのみ `MCP` サフィックスを付与します（例: 「Playwright MCP」）。
- 特定のスキルに対応するドキュメントは、そのスキルと同一の名前を使用します。例えば `opencli-research` スキルは、`docs/integrations.md` 内の OpenCLI セクションに対応付けられます。
- 関連のないドキュメント同士で同一のファイルベース名を共有してはいけません。

### 多言語翻訳アーキテクチャ

正本となるドキュメントは英語で記述され、標準のファイルパスに配置されます。翻訳されたファイルは `docs/i18n/<lang>/` 配下に `<name>.<lang>.md` の形式で配置されます。ルートドキュメントも同様の規約に従います（例: `README.md` は `docs/i18n/zh-Hant/README.zh-Hant.md` に対応）。

翻訳の対象は、`README`、`SECURITY`、`CONTRIBUTING`、`architecture`、`configuration`、`workflows`、`projection`、`integrations`、`setup` という閉じた公式ドキュメント群に限定されています。`docs/adr/` 配下の決定記録は英語専用であり、翻訳ツリーは持ちません。また、英語の命名権威は全文翻訳ではなく、各ロケールの `terminology.<lang>.md` 表示プロファイルを通じて表現されます。

翻訳で変更されるのは地の文（prose）のみです。コマンド名、コード、パス、設定キー、識別子は一切翻訳しません。相対リンクは各言語ディレクトリの階層深度に合わせて再計算されます。

### 翻訳鮮度の追跡

README 以外の翻訳ファイルには、Open Knowledge Format メタデータに加えて 4 つの由来キー（provenance key）が付与されます。翻訳版 README は、この 4 つのキーだけをタイトル直後の非表示の `gal:translation-metadata` HTML コメントに保存します。

```yaml
---
source: README.md          # 英語正本への相対パス
lang: ja
source_commit: <hash>      # 翻訳元となった英語正本のコミットハッシュ（ドラフト時は PENDING）
translated_at: 2026-06-02  # 翻訳を更新した日付
---
```

翻訳の鮮度は `status` ではなく `source_commit` に基づいて評価されます。`status` フィールドはドキュメントのライフサイクル成熟度（`draft`、`stable`、`deprecated`）を表すものであり、翻訳の鮮度を示す目的で使用してはいけません。

`gal translation-freshness` コマンドは、`source_commit` と最新の Git コミット履歴を比較し、各ファイルを `current`、`stale`、`missing`、`unexpected` のいずれかとしてレポートします。検証ロジックは `crates/cli/src/gal/translation.rs` にあります。`crates/cli/src/commands/system.rs` の `cmd_translation_freshness` がこれを呼び出します。新しく作成されたドラフト翻訳は、英語正本の変更がマージされるまで `source_commit: PENDING` として記録されます。

### Front Matter メタデータ仕様

公開 README を除く管理対象のドキュメントは、以下の 5 つのキーを含む Open Knowledge Format（OKF）の front matter から始まります。README の説明は各言語版のドキュメントマップで管理します。

- `type`: ドキュメント種別（`Guide`、`Reference`、`Architecture`、`ADR`、`Policy`）。
- `title`: ドキュメントのタイトル。
- `description`: `README.md` のドキュメントマップ表と完全に一致する 1 文の要約。
- `tags`: 分類タグの一覧。
- `status`: ライフサイクルの成熟度（`draft`、`stable`、`deprecated`）。

README 以外の翻訳ドキュメントでは、これら 5 つのキーに 4 つの翻訳由来キーが加わり、合計 9 つの front matter フィールドで構成されます。翻訳版 README に OKF の front matter はありません。
