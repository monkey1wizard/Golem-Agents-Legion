# Security Policy

## Supported Versions

Security updates are provided exclusively for the latest release. Older releases do not receive backported security fixes.

## Reporting a Vulnerability

Report vulnerabilities privately using GitHub Private Security Advisories. Do not open public issues for suspected vulnerabilities. The project does not maintain a dedicated security email address.

Maintainers make reasonable efforts to coordinate vulnerability disclosures and patch releases, but do not guarantee a fixed-day SLA. Once a report is submitted, maintainers verify the blast radius, develop a fix, and schedule coordinated disclosure directly within the advisory.

## Security Model

### Assets

The primary assets protected by GAL include:

- `AGENTS.md` generated by `gal init`
- Projected skills, commands, and golem agent definitions
- Machine-local settings in `~/.gal/config/config.json`
- User files under `~/.gal/local/`
- Repository-owned state files in `.dev/`

### Trust Roles

The local operator is trusted. The release supply chain is verified using SHA-256 hashes in `checksums.txt` and keyless cosign signatures. Dispatched executors, executor write-back payloads, imported plans, and imported prompts are treated as untrusted input. Host MCP configuration belongs to the user, and `gal` never modifies host configuration without explicit direction.

### Trust Boundaries

- **Ownership markers**: The GAL ownership marker separates tracked contracts from generated adapters. If an existing file lacks this marker, modification aborts immediately.
- **State isolation**: The `_galProjection` namespace separates GAL-managed state from foreign state. GAL does not manage other top-level keys in `plugins.lock.json`.
- **Inlined contracts**: Inlined contract bytes decouple the control node from remote executors. An executor never reads paths that exist solely on the control node.
- **Local configuration**: The `~/.gal/config/config.json` file is strictly machine-local. Values for `executorRouting`, `sshTarget`, and `remoteWorkdir` must never be committed to a repository or shared across machines.
- **Codex host policy**: Codex approval and sandbox settings are user-managed host configurations; GAL never modifies them. GAL launches the dispatched Codex child with `--dangerously-bypass-approvals-and-sandbox`, so the child runs without the Codex sandbox, like the other executors. The Codex Windows sandbox currently fails before it runs any command, as described in [setup.md](docs/setup.md#known-issue-the-codex-windows-sandbox-fails). Denied operations are never treated as authorized, and unobserved policy states remain unknown.
- **Execution evidence**: Availability checks, process launch, provider responses, process exit, receipt validation, and pipeline gate evaluations are distinct evidence stages. Failure at one stage does not imply or determine the outcome of a later stage. Diagnostic outputs must identify the attempted operation while redacting paths and sensitive data. Diagnostics must never dump configuration files, environment variables, authentication tokens, or credentials.

### Security Invariants

Adapter rendering validates required sections and fails closed on syntax or schema errors. File writes and deletions require valid ownership markers, ensuring only GAL-managed paths can be removed. Plan-scoped cleanup must complete successfully. Otherwise, it records a failure receipt. A single regular expression (`secret_re`) powers both git pre-commit filters and `gal doctor` secret scanning. The installer aborts immediately if SHA-256 checksum or cosign signature validation fails. For Codex setup and recovery procedures, see [setup.md](docs/setup.md#codex-pipeline-execution-setup). For detailed architectural specifications, see [architecture.md](docs/architecture.md), [projection.md](docs/projection.md), [configuration.md](docs/configuration.md), and [workflows.md](docs/workflows.md).

### Attack Surface

Primary attack vectors include untrusted executor inputs and write-back data, imported plans and prompt files, SSH execution lanes defined in `config.json`, environment variable expansion (`${ENV_VAR}`) during MCP host loading, and release asset downloads. Note that `ready-to-finalize` provides cooperative workflow evidence only. It does not provide cryptographic proof of provenance and does not defend against attackers with local write access.

### Local Security Tooling

Local security review plugins can detect common vulnerabilities early, but they are not required dependencies or merge blockers. When review tools flag an issue affecting a trust boundary defined here, the corresponding invariant determines the required remediation. Hardcoded secrets are governed by the `secret_re` check. Adapter ownership markers, executor write-back handling, SSH routing in `config.json`, and imported plan files represent GAL-specific risk areas requiring dedicated review. Report any vulnerability found in a release through the private advisory channel described above.
